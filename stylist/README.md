# AI 패션 스타일리스트

옷장 · 실시간 날씨 · 외출 목적 · 무드 · 체형을 종합해 **오늘 입을 옷 한 벌**을 뽑아주는 웹앱.

## 실행 방법

### 기본 — 파일만 열기

`index.html`을 브라우저로 열면 끝. (빌드 도구·서버·외부 라이브러리 없음)

날씨만 네트워크를 쓰고, 네트워크가 없으면 기온을 직접 입력해 100% 오프라인으로 동작한다.

### 선택 — 네이버 쇼핑 검색까지 쓰기

상품명을 검색해 옷장에 등록하려면 로컬 프록시를 띄운다. ([왜 필요한가](#왜-프록시가-필요한가))

```bash
export NAVER_CLIENT_ID=발급받은_아이디
export NAVER_CLIENT_SECRET=발급받은_시크릿
python3 stylist/proxy.py            # http://127.0.0.1:8765
```

브라우저로 `http://127.0.0.1:8765` 를 연다. 파이썬 표준 라이브러리만 쓰므로 설치할 것이 없다.

환경변수 대신 `stylist/.naver_keys.json` 에 넣어도 된다(깃 제외됨):

```json
{"client_id": "...", "client_secret": "..."}
```

**키가 없거나 프록시를 안 띄워도 앱은 그대로 동작한다.** 상품 검색만 비활성되고,
옷은 지금처럼 직접 등록하면 된다.

#### 애플리케이션 등록해서 키 받기

네이버 계정만 있으면 무료다. 심사·승인 대기 없이 즉시 발급된다.

1. [developers.naver.com](https://developers.naver.com/) 접속 → 네이버 계정으로 로그인
2. 상단 **Application → 애플리케이션 등록** ([바로가기](https://developers.naver.com/apps/#/register))
3. **애플리케이션 이름** — 아무거나 (예: `stylist`).
   ※ 이 이름이 사용자에게 노출되므로 네이버 서비스명을 넣으면 반려될 수 있다
4. **사용 API** — 드롭다운에서 **`검색`** 선택 ← **가장 중요**
5. **비로그인 오픈 API 서비스 환경** — `WEB 설정` 선택 →
   웹 서비스 URL 에 `http://127.0.0.1:8765` 입력
6. **등록하기** → 발급된 **Client ID / Client Secret** 확인
   (이후에는 *내 애플리케이션 → 개요* 에서 다시 볼 수 있다)

발급 후 **내 애플리케이션 → API 권한관리** 탭에서 `검색` 이 체크돼 있는지 확인한다.
체크가 안 돼 있으면 호출이 `403` 으로 떨어진다.

##### 참고

- 5번의 웹 서비스 URL 은 **비로그인 오픈 API(검색)에서는 호출 제한에 쓰이지 않는다.**
  인증은 오직 `X-Naver-Client-Id` / `X-Naver-Client-Secret` 헤더로만 이뤄지므로,
  서버 사이드에서 부르는 이 프록시는 URL 값과 무관하게 동작한다.
  다만 등록 폼의 필수 항목이라 값은 채워야 한다.
- 검색 API 에는 일일 호출 한도가 있다. 정확한 수치는
  [API 권한 설정 및 호출 방법 가이드](https://developers.naver.com/docs/common/apicall/)에서 확인한다.
  개인이 옷 등록용으로 쓰는 수준에서는 문제되지 않는다.

##### 오류가 나면

| 증상 | 원인 |
|---|---|
| `401` / 인증에 실패했습니다 | Client ID·Secret 오타, 또는 프록시 재실행 안 함 |
| `403` / API 권한 없음 | *API 권한관리* 에서 `검색` 미체크 |
| 앱에 “키 없음” 표시 | 환경변수가 프록시 프로세스에 전달되지 않음 |

## 이 앱이 답하는 질문

- "오늘 12°에 데이트인데, 내 옷장으로 미니멀하게 뭘 입지?"
  → 트렌치코트 + 옥스퍼드 셔츠 + 치노팬츠 + 스니커즈, 이유와 스타일링 팁까지
- "충동구매한 버건디 크롭 니트, 뭐랑 입어야 하지?"
  → 그 옷을 **고정**해두고 나머지를 맞춰준다 (모드 A)

## 기능

### 1. 옷장 등록

카테고리(아우터/상의/하의/신발/악세서리)별로 이름·색상·두께·핏·격식·무드 태그를 등록한다.
브라우저 `localStorage`에만 저장되며 서버로 전송되지 않는다. 처음 열면 샘플 옷장 17벌이 채워진다.

#### 사진 첨부

등록할 때 **📷 사진 첨부** 로 내 옷 사진을 넣을 수 있고, 이미 등록된 옷은 카드의
📷 버튼으로 나중에 붙일 수도 있다. 사진은 옷장 카드와 추천 결과에 썸네일로 나온다.

- **자동 축소** — 원본을 그대로 두면 localStorage(약 5MB)를 금방 넘긴다.
  긴 변 **256px JPEG(품질 0.72)** 로 줄여 저장한다. 한 장에 보통 2~20KB.
- **색상 자동 인식** — 사진 가운데 영역(배경 영향을 줄이려고 중앙 50%만 표본)의
  최빈 색을 뽑아 15종 색상 중 가장 가까운 이름으로 폼을 채운다.
  틀리면 드롭다운에서 고치면 된다.
- **용량 표시** — 옷장 아래에 `3/20벌 사진 · 84KB 사용` 처럼 현재 사용량이 보인다.
  가득 차면 저장을 되돌리고 안내한다(조용히 유실되지 않는다).
- 사진은 다른 데이터와 마찬가지로 **이 브라우저에만** 저장된다. 업로드되지 않는다.

#### 내 옷을 직접 추가하기 (실제 브랜드 옷)

**한두 벌이면 앱에서**, **여러 벌이면 파일로** 넣는 게 빠르다.

**① 앱에서 하나씩** — 옷장 등록 폼에 이름·색상·두께·핏·격식·무드를 넣고 `+ 옷장에 추가`.
이름에 브랜드를 그대로 적으면 된다 (`무신사 스탠다드 트렌치코트`).

**② 파일로 한 번에** — [`closet-template.json`](closet-template.json) 을 복사해 채운 뒤
`가져와서 합치기`(기존에 추가) 또는 `가져와서 교체`로 불러온다.

```json
{
  "app": "stylist", "version": 1,
  "closet": [
    {"cat":"상의","name":"COS 옥스퍼드 셔츠","color":"화이트","warm":2,"fit":"레귤러","form":2,"moods":["미니멀","클래식"]},
    {"cat":"하의","name":"리바이스 501 오리지널","color":"데님블루","warm":2,"fit":"스트레이트","form":1,"moods":["캐주얼"]}
  ]
}
```

| 키 | 값 | 없으면 |
|---|---|---|
| `cat` | `아우터` `상의` `하의` `신발` `악세서리` | **건너뜀** (추측 불가) |
| `name` | 자유 (브랜드명 그대로) | **건너뜀** |
| `color` | 화이트 블랙 그레이 베이지 브라운 네이비 데님블루 카키 레드 오렌지 옐로 그린 블루 퍼플 핑크 | 블랙 |
| `warm` | `1` 얇음 / `2` 보통 / `3` 두꺼움 | 2 |
| `fit` | 오버핏 세미오버 레귤러 슬림 크롭 와이드 스트레이트 스키니 A라인 | 레귤러 |
| `form` | `1` 캐주얼 / `2` 스마트캐주얼 / `3` 포멀 | 2 |
| `moods` | 미니멀 캐주얼 스트릿 그런지 러블리 클래식 스포티 (복수) | `["캐주얼"]` |

`cat` 과 `name` 만 있어도 들어간다. 빠진 값은 기본값으로 채우고 **몇 개를 채웠는지 알려준다.**
`_` 로 시작하는 키는 메모용으로 무시되므로 템플릿의 설명을 지우지 않아도 된다.

> 값을 잘 채울수록 추천이 정확해진다. 특히 `warm`(기온 판단)과 `moods`(무드 매칭)가
> 결과를 크게 좌우한다.

사진은 파일로 넣기 어려우니, 가져온 뒤 옷장 카드의 📷 버튼으로 붙이면 된다.

#### 프리셋에서 고르기 (아무 준비도 필요 없음)

흔한 옷 **102종**을 속성까지 채워서 내장했다. 클릭하면 등록 폼이 채워지고,
색상만 내 옷에 맞게 바꿔 추가하면 된다. 이미 옷장에 있는 항목은 흐리게 ✓ 표시된다.

| 카테고리 | 개수 | 예 |
|---|---|---|
| 아우터 | 26 | 트렌치코트, 레더 라이더 자켓, MA-1, 숏/롱패딩, 셔켓 |
| 상의 | 27 | 옥스퍼드 셔츠, 오버핏 반팔티, 맨투맨, 터틀넥, 크롭탑 |
| 하의 | 24 | 와이드 데님, 블랙 슬랙스, 카고팬츠, 플리츠 스커트 |
| 신발 | 11 | 스니커즈, 첼시부츠, 로퍼, 워커, 샌들 |
| 악세서리 | 14 | 볼캡, 비니, 크로스백, 토트백, 머플러, 시계 |

이름·색·무드로 검색하고 카테고리 탭으로 좁힐 수 있다.
**가입·API키·인터넷이 전부 불필요하다.**

#### 네이버 쇼핑 검색으로 등록 (선택)

프록시를 띄운 경우, 상품명을 검색해 결과 카드의
‘등록 폼에 넣기’를 누르면 상품명·카테고리에서 속성을 **추정**해 폼을 채운다.

| 추정 항목 | 근거 |
|---|---|
| 카테고리 | 네이버 카테고리 우선(`코트`→아우터, `바지`→하의 …), 없으면 상품명 |
| 색상 | 상품명의 색 표현 (`차콜`→블랙, `연청`→데님블루, `아이보리`→화이트 …) |
| 두께 | `패딩`·`기모`·`울`→두꺼움 / `반팔`·`린넨`·`냉감`→얇음 |
| 핏 | `오버핏`·`와이드`·`크롭`·`슬림`·`스키니`·`A라인` |
| 격식 | `슬랙스`·`블레이저`→포멀 / `후드`·`조거`→캐주얼 |
| 무드 | `워싱`·`레더`→그런지, `카고`·`오버핏`→스트릿 … |

추정일 뿐이므로 폼에서 고친 뒤 추가하면 된다. 실제 예:

```
[무신사] 오버핏 트렌치 코트 베이지  →  아우터 · 베이지 · 두꺼움 · 오버핏
와이드 데님 팬츠 연청              →  하의   · 데님블루 · 보통 · 와이드
린넨 반팔 셔츠 아이보리 슬림       →  상의   · 화이트 · 얇음 · 슬림
첼시 부츠 브라운 스웨이드          →  신발 · 브라운 · 얇음 · 레귤러
```

### 2. 실시간 날씨 — 하루 전체를 본다

옷은 하루를 나가서 입는다. 현재 기온만 보면 아침 7°/낮 20° 인 날 아침에 열었을 때
패딩을 추천하게 된다. 그래서 **오늘의 최고·최저와 강수확률**을 같이 받아온다
(같은 호출이라 추가 비용 없음).

| 기준 | 무엇을 정하나 |
|---|---|
| **낮 최고** | 상의 두께 — 낮에 덥지 않게 |
| **아침·저녁 최저** | 아우터 필요 여부와 총 보온량 |
| **일교차 ≥ 8°** | 벗을 수 있는 겉옷에 가점, 낮에 못 들고 다닐 두꺼운 아우터는 감점 |

일교차가 크면 상의는 **낮 기온을 따르게** 하고 최저 기온 기반 총보온량의 구속력을
낮춘다. 그러지 않으면 최저 기온에 끌려 낮에 더운 옷이 뽑힌다.

실제 동작 (최저는 같고 최고만 다른 두 날):

```
최저 7° / 최고 9°   →  데님 자켓 + 그레이 후드티(보통)     하루 종일 추움
최저 7° / 최고 20°  →  데님 자켓 + 검정 반팔티(얇음)       아침엔 걸치고 낮엔 벗기
```

직접 입력에서도 최저·최고를 넣으면 같은 판정이 돌아간다(선택 항목).

- **내 위치** — 브라우저 위치 권한 → 현재 좌표의 기온·체감·날씨코드
- **도시 검색** — 도시명 → 지오코딩 → 날씨
- **직접 입력** — 기온과 날씨를 손으로 넣기 (오프라인 대비)

[Open-Meteo](https://open-meteo.com/) 무료 API를 쓴다. **API 키가 필요 없다.**
위치 좌표는 날씨 조회에만 쓰이고 저장하지 않는다.

#### 신발과 악세서리는 다른 카테고리다

예전에는 `신발·악세서리` 가 한 카테고리라 **슬롯 하나를 놓고 경쟁**했다. 그 결과
26° 스트릿 무드에서 상위 8후보의 신발 자리가 전부 `볼캡 + 크로스백` 이 되어,
**신발이 하나도 없는 코디**를 추천했다. 지금은 둘을 나눠 신발 슬롯과 악세서리 슬롯을
따로 채운다. 신발이 없으면 감점하지만, 악세서리는 없어도 코디가 성립하므로 감점하지 않는다.

예전 데이터(`신발·악세서리`)는 불러올 때 자동으로 갈라진다. 가방·모자·시계 같은
**악세서리 어휘에 걸리면 악세서리, 나머지는 신발**로 본다. 반대로(신발 어휘로 판별) 하면
`나이키 에어포스 1`, `닥터마틴 1461` 처럼 모델명만 있는 이름이 전부 악세서리로 새어
신발이 0개가 된다.

### 3. 옷장 백업 · 코디 카드

`localStorage` 는 브라우저를 바꾸거나 캐시를 지우면 사라진다. 사진까지 넣은 뒤라면
타격이 크므로 파일로 빼두고 되돌릴 수 있게 했다.

| 버튼 | 하는 일 |
|---|---|
| **내보내기 (.json)** | 옷장·사진·착용이력·취향을 한 파일로 저장 |
| **가져와서 합치기** | 기존 옷장에 추가. 같은 카테고리·이름은 건너뛴다 |
| **가져와서 교체** | 전부 교체 (확인 후 진행) |

깨진 항목은 통째로 버리지 않고 건너뛰며, 백업 파일이 아니면 옷장을 건드리지 않고 알린다.

**🖼️ 코디 카드 저장 (PNG)** — 추천 결과를 룩북 카드 한 장으로 뽑는다.

- **왼쪽 — 착장 플랫레이**: 아우터를 뒤에 깔고 그 위에 상의를 얹은 뒤 하의·신발을
  배치해 한 벌로 보이게 그린다.
- **오른쪽 — 아이템 그리드**: 아이템별 도식(또는 등록한 사진).
- **배경**: 코디의 포인트 색에서 톤을 따 착장마다 배경색이 달라진다.
- 2배 해상도(1800×2360). 공유용이라 테마와 무관하게 밝은 카드로 고정한다.

옷 그림은 **종류를 판별해 도식(플랫 드로잉)으로 그린다** — 코트/자켓/패딩/가디건,
셔츠/니트/후드/티, 팬츠/스커트/반바지, 스니커즈/부츠, 가방/모자. 사진을 올린 옷은
사진이 우선이고, 없을 때 도식이 대신 들어간다.

> 실제 상품 사진이나 패션 일러스트를 생성하는 것은 아니다. 등록한 색·핏·종류로
> 실루엣을 그리는 것이므로, 패턴·프린트·소재감은 표현되지 않는다.

> 파일명은 ASCII 로 만든다(`stylist-closet-…json` / `stylist-outfit-…png`).
> 크로미움은 `download` 속성에 한글이 들어가면 이름을 통째로 버리고 확장자 없는
> `download` 로 저장한다 — 실제로 확인한 동작이다.

### 4. 내 체형 프로필

체형은 매일 바뀌는 값이 아닌데 예전에는 새로고침할 때마다 다시 골라야 했다.
이제 **저장돼서 기억되고**, 목적·무드도 마지막 선택이 복원된다.

**복수 선택 가능** — 실제 몸은 한 가지 특징만 갖지 않는다. `키가 작은 편`과
`하체 볼륨`을 동시에 고르면 두 보정이 함께 걸린다.

| 체형 | 전략 |
|---|---|
| 키가 작은 편 | 크롭 상의·턱인·톤온톤 가점, 부피 큰 아우터 감점 |
| 하체 볼륨 | A라인·스트레이트·와이드 + 어두운 하의 가점, 스키니 감점 |
| 상체 볼륨 | 어두운·정돈된 상의 가점, 오버핏 아우터 감점 |
| 마른 체형 | 오버핏·와이드·레이어링 가점 |
| 통통한 체형 | 세미오버·스트레이트 가점, 스키니·크롭 감점 |
| 표준 | 보정 없음 (다른 항목을 모두 끄면 표준) |

여러 개를 골라도 체형이 다른 기준(기온·목적·색)을 압도하지 않도록,
합산 점수를 고른 개수의 제곱근으로 나눈다.

실제 동작 (같은 옷장·같은 날씨에서 체형만 바꿨을 때):

```
표준             →  화이트 셔츠(레귤러) + 블랙 스키니진(스키니)
하체 볼륨        →  화이트 셔츠(레귤러) + 블랙 A라인 스커트     스키니 회피
키가 작은 편     →  블랙 크롭 티(크롭)  + 블랙 스키니진         세로 비율
하체볼륨+키작음  →  블랙 크롭 티(크롭)  + 블랙 A라인 스커트     둘 다 반영
```

**키·몸무게로 제안받기 (선택)** — 키와 몸무게를 넣고 `체형 제안받기`를 누르면
키 160cm 미만이면 `키가 작은 편`, BMI 18.5 미만이면 `마른 체형`,
25 이상이면 `통통한 체형`을 제안한다. **제안일 뿐이므로 칩에서 고치면 된다.**
상·하체 볼륨은 키·몸무게로 알 수 없으므로 직접 고른 값을 그대로 둔다.

체형·키·몸무게는 옷장과 함께 이 브라우저의 `localStorage` 에만 저장된다.

### 5. 사용자 로그 기반 개인화

> 기획 배경과 발전 로드맵은 [PROPOSAL.md](PROPOSAL.md) 참고.

규칙 기반 추천의 한계는 **모두에게 같은 규칙을 적용한다**는 점이다. 같은 기온·같은
목적이어도 어떤 사람은 오버핏을, 어떤 사람은 슬림을 고른다. 그 간극을 로그로 메운다.

> **규칙은 모두에게 같고, 가중치는 각자에게 다르다.**

**수집** — 착용·👍·👎 를 맥락(기온 밴드·목적·무드)과 그 코디를 이룬 옷의
색·핏·무드와 함께 최근 300건까지 기록한다.

**학습** — `착용 +0.6 / 👍 +1.0 / 👎 −1.0` 을 색·핏·무드별로 누적하고
**아이템 등장 횟수**로 나눈다. 로그 건수로 나누면 한 벌만 반복해도 즉시 상한에 닿는다.

**적용** — 아이템당 최대 **±1.2** 를 추천 점수에 더한다.

세 가지 안전장치를 뒀다.

| 장치 | 이유 |
|---|---|
| 로그 3건 미만이면 학습 미적용 | 데이터가 적을 때 섣불리 개인화하면 추천이 더 나빠진다 |
| 아이템당 ±1.2 상한 | 학습이 기온·목적 규칙을 뒤집지 못하게. 상한 없이는 아이템당 2.05까지 올라 다른 기준을 압도했다(측정) |
| 리포트로 전량 공개 + 초기화 | 블랙박스가 되지 않도록. 결과 화면에도 `로그 학습 +1.4` 로 반영량을 표시 |

**📈 내 스타일 리포트** — 좋아하는 색 / 피하는 색 / 선호 핏 / 끌리는 무드와
**한 번도 안 입은 옷**을 보여준다. 학습 기록만 지우는 초기화 버튼이 있고,
옷장·사진은 그대로 남는다.

로그는 브라우저에만 저장되며 옷장 백업 JSON 에 함께 담겨 기기 이동 시 따라간다.

### 6. 착용 이력 · 취향 학습

추천이 완전히 결정적이면 어제 입은 옷이 오늘 또 나온다. 결과 화면의 버튼으로 이를 보정한다.

| 버튼 | 효과 |
|---|---|
| **✅ 오늘 이거 입었어요** | 착용 이력에 기록 → 며칠간 덜 추천 |
| **👍 마음에 들어요** | 그 옷들의 취향 점수 +0.8 (최대 +3) |
| **👎 별로예요** | 취향 점수 −0.8 (최소 −3) |

최근 착용 감점: 오늘 −3.5 / 어제 −2.5 / 3일 이내 −1.2 / 6일 이내 −0.5.
결과 화면에 `오늘 입음`, `👍2` 같은 칩과 점수 반영분이 표시돼 왜 그렇게 나왔는지 보인다.
이력·취향도 옷장과 함께 `localStorage` 에 저장된다.

## 추천 규칙

조합마다 점수를 매겨 정렬한다. **결정적**이라 같은 입력이면 같은 결과가 나온다(시연 안정).

### 탐색 방식과 상한 (숨기지 않는다)

1. **아우터×상의×하의** 조합만 먼저 점수를 매긴다. 신발·악세서리 점수는 이 세 벌에만
   의존하므로 순위를 바꾸지 않는다.
2. 상위 조합 **최대 120개**만 남기되, **한 슬롯의 같은 옷은 최대 6개까지만** 통과시킨다.
   그러지 않으면 잘 맞는 상의 하나가 조합 수백 개를 독점해 후보가 전부 같은 상의가 된다.
3. 남은 조합마다 신발·악세서리 **상위 3개씩**을 붙여 후보를 만든다.
4. 최종 8개는 점수순이 아니라 **겹침 감점**을 적용해 고른다. 이미 뽑힌 후보와 같은 옷을
   쓰면 감점하되 슬롯별 무게가 다르다(상·하의·아우터 2.0 / 신발 1.0 / 악세서리 0.7).
   메인이 같으면 사실상 같은 코디지만 신발만 같은 것은 덜 심각하기 때문이다.

이 상한들 때문에 **이론상 최적 조합이 후보에서 빠질 수 있다.** 대신 100벌 옷장에서
`recommend()` 가 **약 1,100ms → 약 100ms** 로 줄었고(측정), 8개 후보의 상·하의·아우터가
모두 서로 다른 옷이 된다. 상한이 걸리면 콘솔에 몇 개를 잘랐는지 남긴다.

### 기온 밴드 → 필요 보온량·아우터

구간은 **임의로 정한 값이 아니라** 국내에서 널리 쓰이는
[기온별 옷차림](https://namu.wiki/w/기온별%20옷차림) 표를 그대로 따른다.

| 기온 | 밴드 | 통용 표의 권장 옷차림 | 상의 두께 | 아우터 | 필요 보온량 |
|---|---|---|---|---|---|
| 28°↑ | 매우 더움 | 민소매·반팔 | 얇음 | 없음 | 1 |
| 23~27° | 더움 | 반팔·얇은 셔츠 | 얇음 | 얇은 것만 | 1 |
| 20~22° | 따뜻함 | 얇은 가디건·긴팔 | 얇음 | 선택 | 2 |
| 17~19° | 선선함 | 얇은 니트·맨투맨 | 보통 | 선택 | 2 |
| 12~16° | 쌀쌀함 | 자켓·가디건 | 보통 | 권장 | 3 |
| 9~11° | 추움 | 트렌치코트·도톰한 자켓 | 보통 | 필수 | 4 |
| 5~8° | 많이 추움 | 코트·가죽자켓 | 두꺼움 | 필수 | 5 |
| 4°↓ | 매우 추움 | 패딩·두꺼운 코트 | 두꺼움 | 필수 | 6 |

필요 보온량은 `아우터 두께 + 상의 두께` 와 비교하며, 표의 옷차림 단계
(반팔 → 가디건 → 자켓 → 트렌치 → 코트 → 패딩)를 1~6 으로 옮긴 값이다.

상의 두께는 **낮 최고**, 아우터·총보온량은 **아침·저녁 최저** 기온의 밴드를 쓴다.

### 점수 구성

1. **보온 적합성** — 각 옷의 두께가 밴드 목표와 얼마나 맞는지, 아우터+상의 합산 보온량이 필요량과 맞는지
2. **아우터 유무** — 밴드가 요구하는 아우터 정책(없음/얇게/선택/권장/필수) 위반 시 감점
3. **목적(격식)** — 목적별 목표 격식(등교 1.5 ~ 면접 3.0)과의 거리
4. **무드 일치** — 선택 무드 태그를 가진 옷마다 가점, 하나도 없으면 감점
5. **색 조화** — 아래 규칙으로 아이템 쌍마다 점수, 유채색이 3개 이상이면 감점.
   사진을 올린 옷은 **사진에서 뽑은 실제 RGB** 로 판정한다(대표 15색 근사보다 정확).
   HSL 로 변환해 채도가 낮거나 아주 어둡/밝으면 무채로, 그 외에는 색상환 각도로 본다.
6. **신발·악세서리 매칭** — 격식·색이 본 코디와 맞는 것을 자동 선택
7. **비/눈 보정** — 젖는 날씨엔 흰 신발 감점, 방수·기능성 가점
8. **체형 보정** — 아래 표
9. **최근 착용 회피** — 며칠 안에 입은 옷 감점
10. **취향 피드백** — 👍/👎 누적치 반영
11. **로그 학습** — 행동 로그에서 배운 색·핏·무드 선호를 아이템당 ±1.2 내에서 가산

### 색 조화 규칙

각도 경계는 [배색 이론](https://ko.wikipedia.org/wiki/배색)의 표준 배색 유형에서 가져왔다.

| 조합 | 배색 이론상 이름 | 점수 |
|---|---|---|
| 무채·기본색끼리 | 모노톤/뉴트럴 | +2 |
| 무채색 + 포인트 컬러 1개 | 액센트 배색 | +2 |
| 유채색끼리 색상환 25° 이내 | **유사색**(analogous) | +2 |
| 유채색끼리 150° 이상 | **보색·분할보색**(complementary / split-complementary) | +1 |
| 유채색끼리 40~80° | 어느 쪽도 아닌 중간 | 0 |
| 그 외 유채색 충돌 | — | −3 |

유사색은 색상환에서 이웃한 색으로 통일감을 주고, 보색은 마주 보는 색으로
대비를 만든다. 그 사이 구간(40~80°)은 두 효과 어느 쪽도 뚜렷하지 않아 0점이다.

사진이 있는 옷은 이름 대신 사진 RGB 를 HSL 로 바꿔 판정한다.
채도 < 0.22, 명도 < 0.18, 또는 아주 밝고 채도 낮으면 무채로 본다.

## 기술

- 단일 HTML + 바닐라 JS. 빌드 없음, 외부 라이브러리 없음
- 라이트/다크 테마 자동 대응
- 옷장·사진·착용이력·취향은 `localStorage` (`stylist.closet.v1`) 한 곳에 저장
- `proxy.py` — 파이썬 표준 라이브러리만 쓰는 로컬 프록시. 정적 파일 + `/api/*`

### 왜 프록시가 필요한가

네이버 오픈API 는 브라우저에서 직접 부를 수 없다. 확인한 사실:

1. **CORS 미지원** — preflight(`OPTIONS`)가 `405 Method Not Allowed` 로 떨어지고,
   응답에 `Access-Control-Allow-Origin` 헤더가 없다.
2. **커스텀 헤더 필요** — 인증이 `X-Naver-Client-Id` / `X-Naver-Client-Secret`
   헤더로 이뤄지는데, 커스텀 헤더는 preflight 를 유발한다. 즉 1번에서 막힌다.
3. **Secret 노출** — 설령 CORS 가 됐어도 Client Secret 을 HTML 에 박으면
   페이지를 여는 누구나 키를 가져갈 수 있다.

그래서 `proxy.py` 가 키를 들고 대신 호출한다. `127.0.0.1` 에만 바인딩하며
키는 응답·로그 어디에도 싣지 않는다.

| 경로 | 응답 |
|---|---|
| `GET /api/health` | `{"ok":true,"naver":true}` — 프록시 생존 및 키 설정 여부 |
| `GET /api/shop?query=…&display=12` | 상품명·이미지·가격·브랜드·카테고리 |

프런트는 시작할 때 `/api/health` 를 찔러보고, 실패하면 검색 UI 를 숨긴 채
수동 등록 안내를 띄운다. `file://` 로 연 경우도 마찬가지다.

## 한계

- 추천은 **규칙 기반 스크리닝**이다. 소재·패턴·개인 취향은 반영하지 않는다.
- 색 조화는 대표 색상 15종의 색상환 거리로 근사한다. 실제 톤·채도 차이는 반영하지 않는다.
- 옷의 두께·격식·무드는 사용자가 등록한 값을 그대로 믿는다. 잘못 등록하면 추천도 어긋난다.
- 날씨는 오늘 하루(최고·최저) 기준이다. 시간대별 예보는 쓰지 않는다.
- 취향 학습은 옷 단위 가감점이라, 조합 자체의 취향(이 둘은 같이 안 입음)은 배우지 못한다.
- 사진 색상 인식은 중앙 영역의 최빈 색이다. 패턴·체크·배경이 복잡한 사진은 빗나갈 수 있다.
- 사진은 썸네일(256px)로 저장하므로 원본 화질은 유지되지 않는다.
- 상품명 기반 속성 추정은 **키워드 매칭**이다. 상품명에 색·핏이 안 적혀 있으면
  기본값(블랙·레귤러)으로 떨어지므로 폼에서 확인해야 한다.
- 무신사·크림 **구매내역** 자동 연동은 지원하지 않는다. 사유는 아래.

## 쇼핑몰 연동에 대해

### 키 없이 쓸 수 있는 옷 API 는 없다

“가입 없이 옷 정보를 주는 공개 API” 를 찾아 실제로 호출해봤다. 셋 다 CORS 는 열려 있어
브라우저에서 바로 부를 수는 있지만, 데이터가 쓸 수 없는 수준이었다.

| API | 키 | CORS | 실제 의류 데이터 |
|---|---|---|---|
| [DummyJSON](https://dummyjson.com/) | 불필요 | ✅ | **46개** — 가짜 영문 데모 (`Gigabyte Aorus Men Tshirt`) |
| [FakeStore](https://fakestoreapi.com/) | 불필요 | ✅ | **10개** |
| [OpenProductsFacts](https://world.openproductsfacts.org/) | 불필요 | ✅ | 205개이나 슬리퍼·양말 등 바코드 등록품 |

전부 데모·테스트용이고, 결정적으로 **추천에 필요한 두께·핏·무드가 어느 쪽에도 없다.**
그래서 이 앱은 API 대신 **프리셋 카탈로그를 내장**한다. 속성이 이미 채워져 있고,
등록·키·네트워크가 모두 필요 없으며, 오프라인에서도 동작한다.

### 연동한 것 — 네이버 쇼핑 검색 API (선택)

[네이버 검색 API](https://developers.naver.com/docs/serviceapi/search/shopping/shopping.md)
(`openapi.naver.com/v1/search/shop.json`)를 붙였다. 공식·무료이고, 무신사·크림을 포함한
쇼핑몰 상품이 검색 결과에 함께 잡힌다. 상품명으로 검색해 옷장에 등록하는 용도다.

### 연동하지 않은 것 — 무신사·크림 직접 연동

두 곳의 상품·구매내역을 직접 가져오는 기능은 **넣지 않았다.**

- **무신사** — 공개 오픈 API 가 없다. 입점 판매자가 파트너센터에서 발급받는 제한된 API 만
  있고, 그마저 상품수집 기능은 제공하지 않는다. 일반 사용자·서드파티 앱이 쓸 수 있는
  창구가 아니다.
- **크림(KREAM)** — 공식 공개 API 가 없다. 웹의 내부 JSON 엔드포인트를 긁는 서드파티
  스크래퍼가 존재하지만 이용약관 위반이고, 엔드포인트가 바뀌면 바로 깨진다.

또 하나 —— 추천에 실제로 쓰이는 **두께·핏·무드는 쇼핑몰 데이터에도 없는 값**이다.
그래서 어떤 경로로 연동하든 사용자가 확인·보정하는 단계는 남는다. 지금 구조는
검색으로 초안을 채우고 사용자가 고치는 방식이다.
