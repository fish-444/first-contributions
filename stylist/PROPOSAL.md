# AI 패션 스타일리스트 — 기획서

옷장·실시간 날씨·외출 목적·무드·체형을 종합해 **오늘 입을 옷 한 벌**을 제안하는 웹 애플리케이션.

| 항목 | 내용 |
|---|---|
| 산출물 | `stylist/index.html` 단일 파일 (빌드·서버·외부 라이브러리 없음) |
| 실행 | 브라우저로 파일을 열면 끝. 네트워크 없이도 동작 |
| 데이터 | 전량 사용자 브라우저 `localStorage`. 서버 전송 없음 |
| 선택 기능 | 네이버 쇼핑 검색 연동(`proxy.py`, 표준 라이브러리만) |

---

## 1. 왜 만들었는가

### 1.1 문제 정의

옷은 있는데 입을 옷이 없다. 이 흔한 말은 취향이 아니라 **결정 비용**의 문제다.
옷장에 20벌이 있으면 상·하의·아우터·신발 조합만 이론적으로 수천 가지다.
매일 아침 그중 하나를 고르면서 사람은 동시에 여러 조건을 맞춰야 한다.

- 오늘 기온이 몇 도이고 일교차가 얼마인가
- 오늘 어디를 가는가 (등교인가 면접인가)
- 어떤 인상을 주고 싶은가
- 내 체형에서 어떤 실루엣이 사는가
- 색이 서로 부딪히지 않는가

이 다섯을 머릿속에서 동시에 만족시키기 어려우니, 사람은 **결정을 회피**한다.
그 결과가 "매일 입던 것만 입기"이고, 옷장의 나머지는 자산으로만 남는다.

### 1.2 기존 방법의 한계

| 방법 | 한계 |
|---|---|
| 날씨 앱 | 기온은 알려주지만 **내가 가진 옷**을 모른다 |
| 패션 SNS·룩북 | 남의 옷이다. 내 옷장에 없는 조합이라 실행할 수 없다 |
| 쇼핑몰 추천 | 목적이 **구매 유도**다. 이미 가진 옷을 활용하도록 돕지 않는다 |
| 스타일링 앱 | 옷을 일일이 등록해야 하는 진입 장벽, 추천 근거를 알 수 없는 블랙박스 |

공통점은 **"내 옷장 × 오늘의 조건"이라는 교집합을 다루지 않는다**는 것이다.

### 1.3 설계 목표

1. **가진 옷으로 해결한다** — 새로 사지 않아도 되는 조합을 먼저 제안한다.
2. **이유를 말한다** — 왜 이 옷인지 기온·목적·무드·체형 근거를 함께 보여준다.
3. **진입 장벽을 없앤다** — 가입·API 키·인터넷 없이 즉시 동작한다.
4. **데이터를 가져가지 않는다** — 옷장·사진·위치가 기기 밖으로 나가지 않는다.

## 2. 왜 필요한가

### 2.1 실행 가능한 제안이어야 한다

패션 정보는 이미 넘친다. 부족한 것은 **지금 내가 실행할 수 있는 한 벌**이다.
본 서비스는 사용자가 등록한 옷 안에서만 조합을 만든다. 추천된 코디는
옷장을 열면 그대로 존재하므로 **제안과 실행 사이의 거리가 0**이다.

### 2.2 하루 단위 날씨 판단이 필요하다

옷은 하루를 나가서 입는다. 현재 기온만 보면 아침 7°/낮 20°인 날 아침에
패딩을 권하게 된다. 그래서 **오늘의 최고·최저와 일교차**를 함께 본다.

| 기준 | 결정하는 것 |
|---|---|
| 낮 최고 | 상의 두께 (낮에 덥지 않게) |
| 아침·저녁 최저 | 아우터 필요 여부와 총 보온량 |
| 일교차 ≥ 8° | 벗을 수 있는 겉옷 우대, 낮에 못 들고 다닐 두께는 감점 |

실측: 최저가 같아도 최고가 다르면 결과가 갈린다.

```
최저 7° / 최고 9°   →  데님 자켓 + 그레이 후드티(보통)     하루 종일 추움
최저 7° / 최고 20°  →  데님 자켓 + 검정 반팔티(얇음)       아침엔 걸치고 낮엔 벗기
```

### 2.3 근거 있는 규칙이어야 한다

추천 규칙의 수치를 임의로 정하지 않았다.

| 규칙 | 근거 |
|---|---|
| 기온 8구간 (28/23/20/17/12/9/5/4°) | 국내에서 통용되는 **기온별 옷차림 표** (반팔→가디건→자켓→트렌치→코트→패딩) |
| 색 조화 각도 (25° / 150°) | **배색 이론**의 유사색(analogous)·보색/분할보색(complementary) |
| 체형 보정 | 시선 분산·세로 라인 등 일반 스타일링 원칙을 규칙으로 명문화 |

### 2.4 프라이버시가 전제되어야 한다

옷장 사진과 위치는 민감한 개인 정보다. 본 서비스는 **서버가 없다.**
사진은 256px 썸네일로 브라우저에만 저장되고, 위치 좌표는 날씨 조회에만 쓰고 버린다.
"업로드하지 않는다"가 정책 선언이 아니라 **구조적으로 불가능**하다.

## 3. 기대 효과

### 3.1 사용자

| 효과 | 근거 |
|---|---|
| **아침 결정 시간 단축** | 수천 조합을 8개 후보로 압축. 마음에 안 들면 '다시 뽑기' |
| **옷장 활용률 상승** | 리포트가 "한 번도 안 입은 옷"을 드러내고, 최근 착용 옷은 감점해 순환시킨다 |
| **충동구매 후회 감소** | 모드 A는 새로 산 옷을 고정하고 나머지를 맞춰, 그 옷이 사장되지 않게 한다 |
| **스타일링 학습** | 추천마다 이유와 팁을 제시해 다음엔 스스로 판단할 수 있게 한다 |

### 3.2 사회·환경

의류 폐기의 상당 부분은 "안 입어서" 발생한다. 가진 옷의 조합 가능성을 드러내는 것은
**새 옷 구매를 대체**하는 효과가 있다. 옷장 활용률을 올리는 것은 그 자체로
의류 소비를 줄이는 방향이다.

### 3.3 기술

- **오프라인 우선 설계** — 단일 HTML로 빌드·서버 없이 완결. 배포·유지 비용이 0에 수렴
- **설명 가능한 추천** — 점수 구성을 화면에 노출(색 조화, 최근 착용 −3.5, 로그 학습 +1.4).
  블랙박스가 아니므로 사용자가 납득하고 교정할 수 있다
- **결정적 동작** — 같은 입력이면 같은 결과. 시연·검증·재현이 가능하다

## 4. 발전 방향 — 사용자 로그에 맞춰 진화한다

### 4.1 핵심 방향

규칙 기반 추천의 한계는 명확하다. **모두에게 같은 규칙을 적용한다는 점**이다.
같은 기온·같은 목적이어도 어떤 사람은 오버핏을, 어떤 사람은 슬림을 고른다.

본 서비스는 이 간극을 **사용자 행동 로그**로 메운다.
규칙은 출발점이고, 쓸수록 그 사람에게 맞춰진다.

> **핵심 원칙: 규칙은 모두에게 같고, 가중치는 각자에게 다르다.**

### 4.2 이미 구현된 것 (1단계 — 개인 로그 학습)

사용자의 행동을 **맥락과 함께** 기록하고, 그 로그에서 선호를 학습해 점수에 반영한다.

**수집하는 로그** (최근 300건, 브라우저 내부에만 저장)

| 필드 | 내용 |
|---|---|
| 행동 | `착용` / `👍` / `👎` |
| 맥락 | 기온 밴드, 외출 목적, 선택 무드 |
| 대상 | 그 코디를 이룬 옷들의 색·핏·무드 |

**학습 방식**

```
착용 = +0.6 (약한 긍정)   👍 = +1.0 (강한 긍정)   👎 = −1.0 (부정)
  ↓
색·핏·무드별 선호도 = 누적 점수 / 아이템 등장 횟수
  ↓
추천 점수에 아이템당 최대 ±1.2 만큼 가산
```

**세 가지 안전장치**

1. **콜드 스타트 차단** — 로그 3건 미만이면 학습을 적용하지 않는다.
   데이터가 적을 때 섣불리 개인화하면 오히려 추천이 나빠진다.
2. **상한 (±1.2/아이템)** — 학습이 기온·목적 같은 기본 규칙을 뒤집지 못하게 묶는다.
   상한이 없으면 로그가 조금만 쌓여도 학습이 다른 기준을 압도한다(실측 2.05 → 0.76으로 조정).
3. **투명성** — 무엇을 배웠는지 **내 스타일 리포트**에서 그대로 보여주고,
   추천 결과에도 `로그 학습 +1.4` 처럼 반영량을 표시한다. 언제든 초기화할 수 있다.

**사용자가 보는 것 — 내 스타일 리포트**

| 항목 | 예시 |
|---|---|
| 좋아하는 색 | 블랙 +0.67, 화이트 +0.33 |
| 피하는 색 | — |
| 선호하는 핏 | 오버핏 +0.50 |
| 끌리는 무드 | 캐주얼 +0.42, 미니멀 +0.31 |
| 한 번도 안 입은 옷 | 트렌치코트, 라이더 자켓 외 4벌 |

### 4.3 다음 단계 (2단계 — 맥락별 개인화)

지금은 색·핏·무드를 **전체 평균**으로 학습한다. 다음은 **맥락별로 쪼개는 것**이다.

- `면접일 때의 나`와 `약속일 때의 나`는 다른 사람이다 → 목적별 선호 분리
- `여름의 나`와 `겨울의 나`도 다르다 → 기온 밴드별 선호 분리
- 선택한 무드와 실제 채택한 옷의 무드가 어긋나면 → **"말한 취향"과 "실제 취향"의 차이**를 짚어준다

### 4.4 다음 단계 (3단계 — 조합 단위 학습)

현재 학습은 **옷 단위**다. "이 둘은 같이 안 입는다" 같은 **조합 수준의 취향**은 배우지 못한다.
착용 로그에서 함께 등장한 쌍/등장하지 않은 쌍을 집계해 조합 친화도를 학습하면,
개별 옷은 좋아하지만 같이는 안 입는 경우를 구분할 수 있다.

### 4.5 다음 단계 (4단계 — 로그 기반 검증)

축적된 로그는 **추천 품질의 평가 지표**가 된다.

| 지표 | 의미 |
|---|---|
| 채택률 | 추천 8개 중 실제로 입은 비율 |
| 순위 정확도 | 채택된 코디가 몇 번째 후보였는가 |
| 다시 뽑기 횟수 | 적을수록 첫 제안이 좋았다는 뜻 |
| 옷장 활용률 | 기간 내 착용된 옷 / 전체 옷 |

이 지표들로 **규칙 변경 전후를 비교**할 수 있다. 개인화가 실제로 추천을 개선하는지
로그로 증명하는 것이 최종 목표다.

### 4.6 로그 정책

| 원칙 | 내용 |
|---|---|
| 저장 위치 | 사용자 브라우저 `localStorage`. 서버 전송 없음 |
| 보관량 | 최근 300건 (초과분 자동 폐기) |
| 통제권 | `학습 기록 초기화` 버튼으로 언제든 삭제. 옷장·사진은 유지 |
| 투명성 | 학습 내용과 반영량을 화면에 그대로 노출 |
| 이식성 | 옷장 백업(JSON)에 함께 포함돼 기기 이동 시 따라간다 |

## 5. 현재 구현 상태

| 기능 | 상태 |
|---|---|
| 옷장 등록 (직접·프리셋 102종·사진·JSON 일괄) | 완료 |
| 실시간 날씨 (최고/최저/일교차/강수확률) | 완료 |
| 규칙 기반 추천 엔진 (11개 항목 점수화) | 완료 |
| 체형 프로필 (복수 선택·키/몸무게 제안·저장) | 완료 |
| 착용 이력 / 취향 피드백 | 완료 |
| **사용자 로그 학습 + 스타일 리포트** | **완료 (1단계)** |
| 옷장 백업·복원 (JSON) | 완료 |
| 코디 카드 이미지 (룩북 PNG) | 완료 |
| 네이버 쇼핑 검색 연동 (선택) | 완료 |
| 맥락별 개인화 (2단계) | 계획 |
| 조합 단위 학습 (3단계) | 계획 |
| 로그 기반 품질 지표 (4단계) | 계획 |

### 성능

100벌 옷장 기준 추천 계산 **약 100ms**.
2단계 탐색(조합 선별 → 신발·악세서리 부착)과 슬롯별 쿼터로 약 1,100ms에서 단축.

### 한계 (명시)

- 규칙 기반 스크리닝이다. 소재·패턴·프린트는 반영하지 않는다.
- 색 조화는 대표 15색 또는 사진의 대표 RGB로 근사한다.
- 탐색에 상한이 있어 이론상 최적 조합이 후보에서 빠질 수 있다(콘솔에 기록).
- 학습은 옷 단위이므로 조합 자체의 취향은 아직 배우지 못한다.
- 추천 품질을 증명할 정량 지표가 아직 없다(4단계 과제).
